=======================================================================
Testing the native Wayland backend
=======================================================================

xwpe has a native Wayland backend (we_wayland.c): the graphical xwpe / xwe
run directly on a Wayland compositor (wl_surface + xdg-shell, wl_shm buffers,
wl_keyboard / wl_pointer via xkbcommon, wl_data_device clipboard) with no X
server and no XWayland.  It is selected automatically when WAYLAND_DISPLAY is
set; force the X11 path with `xwpe -display :0` or an unset WAYLAND_DISPLAY.

This file covers how the backend is tested: what the automated suite checks,
and the short manual checklist for the things a headless runner cannot.


1. Automated suite (tests/wayland/)
-----------------------------------------------------------------------
The Wayland counterpart to tests/x11/.  Same SCREENCELL grid and Cairo
renderer, driven over wl_keyboard / wl_pointer instead of Xlib, so a
regression in the Wayland input/render path is caught.  It mirrors the X11
modules (a shared run_x11_module helper runs the X11 test bodies under the
Wayland fixture, so the two suites cannot drift) and adds Wayland-specific
tests: resize/relayout, a wl_pointer scrollbar drag, and wl_data_device
clipboard interop.

The size of the committed frame has its own rows (tests/wayland/
test_surface_bound.py): one starts the editor on a headless weston whose output
is smaller than the editor's own window (a fullscreen bound), the other shrinks
and grows the output under CPU load (busy processes started through the
owner, gui_owner.start_hogs: XWPE_TEST_LOAD=<n> if larger, at least 4) and
judges the editor by libwayland's own wire log (WAYLAND_DEBUG=1), which must
also show the 30x6 minimum size announced and no refused present in the frame
trace.  Two more rows run the editor on a weston of their own over a larger X
screen and resize the output by a few pixels with the pointer left alone: the
configure must be acked on the wire within a deadline, and SIGTERM after it
must still end the editor with its work in the .ESV file.  Whether libwayland's
dispatch loop waits for a default-queue event depends on how the compositor
batches its events, so those rows are end-to-end evidence; the deterministic
guard of that wait is tests/test_wlframe.c.  XWPE_WL_FRAME_TRACE=/path makes the editor write one line
per configure, apply, ack and commit, for chasing a window of the wrong size;
tests/test_wlframe.c (make check) runs the same state machine with no
compositor.

The lost display has its own rows (tests/wayland/test_display_lost.py, and
tests/x11/test_display_lost.py for the X server): each starts an X server (and
a weston) of its own, types text, ends the compositor through the owner, and
asserts that the editor exits with code 1 within a scaled deadline, prints
"xwpe: connection to the Wayland compositor lost", and leaves the text in
t.c.ESV.  A second row does the same at a stop under the stand-in dbx, which
must be told to quit and go.  The rows declare the loss and the exit
(expect_display_loss, expect_exit(code=1)).

Run it:

    tests/run-tests.sh --wayland
    # or directly:
    XWPE_BIN=$PWD/xwpe tests/.venv/bin/python -m pytest -q tests/wayland/

Requirements (Debian package names); the suite skips cleanly if any is
missing:

    xvfb            headless X server (weston takes its input from it)
    weston          a real Wayland compositor (x11-backend + kiosk-shell)
    xdotool         synthetic key / mouse (delivered to weston's X seat)
    wl-clipboard    wl-copy / wl-paste, for the clipboard interop test
    python3-pil     Pillow, to load frame dumps and assert on pixels

How the pipeline gets synthetic input into a wl_client: Xvfb gives weston
(its x11-backend) a seat whose keyboard/pointer come from the X server, so
xdotool's XTEST events arrive at xwpe as wl_keyboard / wl_pointer events.
xwpe mirrors every painted frame to a PPM via XWPE_WL_DUMP -- a race-free
screenshot of the wl_shm buffer, since weston-x11 renders through GL that
`xwd` cannot read.  Most tests assert on the file written to disk (ground
truth); a few assert on the dumped pixels.

CI: .github/workflows/linux.yml runs this suite on every dispatch, as shards of
the one suite plan (tests/harness/suite_plan.py): every row of tests/wayland is
collected, placed in a shard of its own layer, and cut after that shard's own
minutes, with the junit of every row it finished kept.  The resize/relayout
parity rows are the layer's BLOCKING gate: one of them that failed, or that no
shard's junit holds, fails the run.  Every other wayland row is shown and not
gated, because the shared GitHub runner is too slow to run the whole
real-compositor stack flake-free as a hard gate.  A display shard runs one
pytest process and no row twice, so a row that fails under load stays failed
(the conftest refuses --reruns).


2. Manual checklist (what the headless suite cannot assert)
-----------------------------------------------------------------------
The automated suite runs under Xvfb + weston, which is deliberately minimal.
Before a release, sanity-check the backend on a real desktop; these are the
things the emulated pipeline does not cover:

  [ ] Runs on a real GNOME (Mutter) and a real KDE (KWin) Wayland session,
      and on a wlroots compositor (sway).  Window opens, is decorated, and
      can be moved and resized.
  [ ] HiDPI / fractional scaling: text is crisp (not bitmap-scaled) at
      200% and at 150% fractional scale; the grid refits on a scale change.
  [ ] Interactive resize is smooth -- no flicker, no line shear, no crash --
      including a fast drag and a maximize/unmaximize.
  [ ] Maximize and unmaximize on weston's desktop shell and on KWin/Mutter:
      the editor fills the window to its edge (a black strip past the last
      cell is right), nothing is cut, and the editor survives.
  [ ] Drag the window narrower than 30 cells: the grid stops shrinking, the
      right edge is cut, nothing crashes.
  [ ] Resize the window while File > Shell runs a command: the frame stays as
      it was and the compositor does not disconnect the editor; it refits when
      the command ends.
  [ ] End the compositor from a TTY (kill its PID) while xwpe holds unsaved
      text: in the terminal xwpe was started from, one line says the
      connection to the compositor was lost and the .ESV file is named;
      "xwpe -r" brings the text back.  A protocol error shows its interface
      and code in that line.
  [ ] The X11 fallback of the lost-display end (libX11 before 1.7, no exit
      handler) is checked by hand: no committed row can force it, and none
      can tell whether its last step (ending the children of an end already
      running, wpe_child_end_from_handler in e_display_lost_exit) ran, because
      the end ends them as well.  Copy the tree, run configure, change the line
      "#define HAVE_XSETIOERROREXITHANDLER 1" of config.h to a comment, make,
      and run tests/x11/test_display_lost.py with XWPE_BIN pointing at that
      build: every row must pass.  Then, under a debugger stop, send SIGTERM to
      xwpe and end the X server at once: the debugged program must be gone.
  [ ] Clipboard interoperates with other Wayland apps in both directions:
      copy in xwpe -> paste in a browser/terminal, and back.  Both CLIPBOARD
      (Ctrl-C/V) and PRIMARY (middle-click) selections.
  [ ] Keyboard: national layouts and dead-key compose produce accented
      characters; held keys autorepeat; modifiers (Alt/Ctrl/Shift) reach the
      menus.
  [ ] Pointer: scrollbar drag, mouse-wheel scroll (both axes), and window
      drag/resize via the title bar behave like the X11 build.
  [ ] Debugger: while gdb runs a program that waits for input, Debug > Quit
      (Alt-D, Q) from the menu ends gdb, F8 says the program is running, and
      a typed line reaches the program.  The headless twins run it
      (tests/wayland/test_menu_debug.py); the check here is the same on a
      real desktop, where the editor is started from a launcher with no
      terminal on its input.
  [ ] Debugger Pause: while gdb runs a program that does not stop (a loop,
      a sleep), Ctrl-Break (Ctrl+Pause on a PC keyboard) stops it, the line
      it was on is marked and the status row says "Paused".  The key
      translation is asserted by tests/test_wayland_keysym.py and the session
      by test_ctrl_break_pauses in tests/wayland/test_menu_debug.py; the
      check here is the key on a real keyboard and compositor.
  [ ] Output under a dialog: while gdb runs a program that prints all the
      time, Search > Find opens its dialog; nothing in the window changes
      while it is up, and once Esc closes it Messages scrolls on with what
      was printed meanwhile.  The X11 twin is
      tests/x11/test_screen_owner.py.
  [ ] User Screen: after a Ctrl-F9 Run or a debug session that printed,
      Alt-F5 shows the program's screen in the editor's own colours and a
      key returns to the editor.  Automated by tests/wayland/test_user_screen.py
      and the User Screen row of tests/wayland/test_screen_owner.py.
  [ ] File drag with a long path: open two file managers (F3 twice) side by
      side, the second in a folder of about 4000 characters, and drag a file
      with a 200 character name from the first onto the second.  Nothing is
      copied, moved or linked, and a box says "The target file path is longer
      than the system allows (4096 bytes)."  Not automated: it needs the two
      windows laid out side by side and a drag between their rows.  The
      refusal itself is asserted at the C level by tests/test_path.c (a
      4000 byte folder joined with a 200 byte name).
